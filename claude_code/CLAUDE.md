## 共通設定

- 日本語で出力すること
- WebFetchの代わりにmcp__readability__read_url_content_as_markdownを使用する

## 全プロジェクト共通のルール

任意の、開発のプロジェクトについて以下を守ること

- 以下のケースを除き、コードを書く時はテストコードもセットで書くこと
  - Terraform等のIaC
  - ApacheやRDB等の設定ファイル
  - 単純なDto等のクラス
- 実行環境やTerraform等は全てDockerで準備すること
  - さらに、ローカルでの動作確認用としてdocker-compose.yamlを準備すること
- ファイルを作成する時は末尾に改行を入れること
- **ドキュメントの現在性**: 任意のドキュメントを書く際は、常に現在の状態を記述すること
  - 時系列的な表現（「新機能」「追加された」「今後」「最近追加された」など）を避ける
  - 機能の説明は現在の動作を記述する
  - 変更履歴が必要な場合は別のセクション（CHANGELOG、Git履歴など）に記載する
  - ドキュメントを読む人は「今この機能がどう動作するか」を知りたいのであって、「いつ追加されたか」や「これは新機能であるということ」は知る必要がない
  - 実装時の文脈（「今追加している」）をドキュメントに持ち込まない

## 高価格モデル（Fable等）でオーケストレーションする際の注意

上位・高価格モデルをオーケストレータにしてサブエージェントへ作業を委任する場合、以下を守ること。

### モデルの割り当て

- 実装（ファイル読み書き・テスト実行・反復）はトークン消費が重いので、安価で有能なモデル（Sonnet等）に委任する
- レビュー・仕様/品質の分析は上位モデル（Opus等）に委任する。バグ発見のROIが高く投資に見合う
- レビューは実装したエージェントとは別のモデル/エージェントに行わせる（自作の自己レビューは弱いため独立性を確保する）
- 最上位モデル（Fable等）をオーケストレータに使うのは、統括の判断そのものが非常に難しい場合に限る。そうでなければオーケストレータもOpus等に下げてプレミアムを節約する

### オーケストレータのコンテキストを汚さない（最重要）

- 最上位モデルのコンテキストは最も高価。低価値なトークンを流し込まないこと
- 長時間サブエージェントを `TaskOutput` の block=true でポーリングしない。完了通知が自動で届くのでそれに任せる
- サブエージェントの生の会話トランスクリプト（JSONL等）をオーケストレータのコンテキストに取り込まない。エージェントの最終報告だけを読む
- オーケストレータの仕事はタスク分解・タスク仕様の作成・受け入れ可否の判断・最終検証に絞る

### サブエージェントの使い回し

- 密結合な逐次作業は同一エージェントを SendMessage で使い回すと、コンテキスト/キャッシュを引き継げて効率的
- ただしコンテキストは単調増加しキャッシュ読み込みコストが膨らむ。マイルストーンの節目でエージェントを切るか判断する
