# 実行可能GOAL作成(計画フェーズ支援)

## このスキルが解く問題

高価で難しい「統括の判断」(何を作るか・どう分解するか・どの設計を採るか・却下するか)は、上位モデルとの対話でしか良質に定まらない。一方その判断が済んでしまえば、実行(実装・テスト・修正)は安価なモデルのオーケストレーションで回せる。

この非対称を活かすのが2フェーズ運用:

- **フェーズ1(計画・このスキルの対象)**: 上位モデルと対話し、難しい判断を **GOAL.md + 検証コード** に外部化する
- **フェーズ2(実行)**: 別の新規セッションで `/goal` にGOAL.mdを食わせ、マイルストーン単位で「実装→独立レビュー→修正→検証」ループを回す

**成果物の絶対条件**: 対話の記憶がゼロの新規セッションが、この成果物**だけ**で実行でき、いつ完了かを計画者に聞かずに判定できること。ここに計画者の推論が欠けていると、実行セッションがそれを再導出する羽目になり、2フェーズにした意味が消える。

**GOAL.md と検証コードは一時的な足場**: これらは実行フェーズへの引き渡し専用であり、タスク完了後に破棄される前提で書く。リポジトリに恒久的に残るのは、実装コード・恒久テスト・ドキュメントだけ。したがって:

- 恒久ファイル(実装コード、コード内コメント、恒久テスト、README等)に **GOAL.md や検証コードへの参照を残さない**。「このタスクで」「今回追加する」等の時系列・タスク文脈も持ち込まない(現在の振る舞いだけを書く)。
- 検証コードのうち、恒久的な回帰保護に値するもの(機能の不変条件を守るテスト)は、実行フェーズで**既存の恒久テストへ移植**する。使い捨ての受け入れスモーク(E2E等)と区別してGOAL.mdに書き分ける。
- 最後のマイルストーンの受け入れゲートに「**GOAL.md と検証コードを削除しても、恒久テストが緑で機能と回帰保護が成立する**」を必ず含める。これが「一時物への依存が恒久側に漏れていない」ことの機械的な担保になる。
- **削除は自動実行せず、直前にユーザーへ確認する**。GOAL.mdには設計判断・却下案・凍結契約といった、コードからは復元できない情報が入っている。破棄前に「(A) 恒久ドキュメント(設計判断記録・ADR・README等)へ要点を残してから削除 / (B) 残さずに削除」を必ず質問し、回答を得てから削除する。GOAL.mdの最終マイルストーンにこの質問を明記し、実行セッションが勝手に判断しないようにする。
- (A)を選んだ場合に残すのは、GOAL.mdの**丸ごとコピーではなく**、恒久的に価値のある部分だけ: 技術方針とその理由・不採用案とその理由・凍結契約。ゴール/マイルストーン/受け入れゲートといった進行管理の記述は残さない。残す文書も現在形で書き、タスク文脈や時系列表現・GOAL.mdへの参照を持ち込まない。

## 進め方

### 1. インタビュー(難しい判断を引き出す)

実装に飛びつかず、まず対話で以下を確定する。曖昧さ・トレードオフ・却下した代替案こそが、実行者が最も詰まる箇所なので重点的に掘る。

- ゴールと「完了の定義」。何ができたら終わりか
- スコープと非ゴール。やらないことを明示する
- 制約(不変条件)。局所的に妥当でも全体で誤る選択を封じるもの
- 成功基準。客観的・検査可能にする(理想は各基準がテストに対応)
- 決定済みの技術方針・アーキテクチャと**その理由**。特に検討して**却下した案とその理由**
- 凍結すべき契約(変更禁止のデータ形式・IF)があるか

ユーザーが答えを持っていない箇所は、選択肢と推奨を提示して一緒に決める。ここが計画セッションの本体。

### 2. GOAL.md を書く

`references/goal-template.md` の節構成に沿って書く。各節が「なぜ必要か」はテンプレート内に記載。時系列表現を避け、現在の状態を記述する(「追加する」でなく「こう動く」)。

### 3. 検証コードを用意する

GOAL.mdだけでは実行セッションは自己検査できない。**検証コードが客観的な受け入れゲート**になる。

- 成功基準を符号化したテスト(各マイルストーンの合否を機械的に判定できる)
- デモ/例の入力。回帰フィクスチャ 兼「本当に動くか」のスモーク(例: ある不具合を仕込んだ入力→期待される反例)
- これらがあると、実行セッションは判断力なしで「通ったか」を確認しながら進める

### 4. 実行可能リトマス試験をかける

引き渡す前に `references/authoring-checklist.md` で自己点検する。核心は一つ:

> この成果物だけを渡されたコンテキスト無しのオーケストレータが、あらゆる分岐で正しく決定でき、完了を計画者に聞かず判定できるか?
> どこかで計画者の推論を再導出する必要があれば、その推論が成果物から欠けている → GOAL.mdに書き足す。

### 5. 実行セッションへ引き渡す

- GOAL.md・検証コード・関連資料がリポジトリに揃い、新規セッションが「ここから読む」で辿れる状態にする
- 実行は別セッションで `/goal <GOAL.mdのパスと補足>` を叩く。オーケストレータのモデル選定・サブエージェント運用は `agent-orchestration` スキルに従う(実装=安価モデル、レビュー=上位モデル、統括は判断が本当に難しい時だけ最上位)

## アンチパターン(やってはいけない)

- **理由なしの決定を並べる**: 「Xを採用」だけ書くと実行者が却下済みの代替案を再発見して蒸し返す。理由と「不採用」案を必ず添える
- **成功基準が主観的**: 「使いやすく」等は検査不能。客観的な基準+テストに落とす
- **一枚岩の巨大ゴール**: 独立に検証できるマイルストーンに割る。各塊に受け入れゲートを付ける
- **凍結契約を書かない**: 変更禁止の形式・IFと「Xを変えるならYも同時更新」ルールを明記しないと、実行者が契約を壊す
- **計画セッションで実装まで走る**: このスキルの成果物は設計・計画・検証コードの骨組み。本実装は実行フェーズの仕事
- **一時物(GOAL.md/検証コード)への依存を恒久側に残す**: 恒久ファイルがGOAL.mdを参照したり、タスク文脈・時系列表現を含むと、GOAL.md破棄後に意味が欠ける。恒久テストへ移植すべきものと使い捨てのものを書き分け、削除しても成立する状態を最終ゲートで確認する
