# 実行可能GOAL 引き渡し前チェックリスト

GOAL.mdと検証コードを実行セッションへ渡す前に自己点検する。**核心の問い**:

> この成果物だけを渡されたコンテキスト無しのオーケストレータが、あらゆる分岐で正しく決定でき、完了を計画者に聞かず判定できるか?

各項目で「No」があれば、その情報が成果物から欠けている。GOAL.mdか検証コードに足してから渡す。

## 完了判定できるか

- [ ] 「完了の定義」が一文で書かれている
- [ ] 成功基準がすべて客観的で、機械的または明確な手順で検査できる(主観語がない)
- [ ] 各成功基準に対応する検証(テスト or スモーク手順)が存在する
- [ ] マイルストーンごとに受け入れゲート(合否条件)がある

## 分岐で正しく決定できるか

- [ ] 主要な設計判断が「理由付き」で書かれている(実行者が再議論しなくて済む)
- [ ] 検討して却下した案とその理由がある(実行者が却下済みの道を蒸し返さない)
- [ ] 非ゴールが明示され、脱線の範囲が閉じている
- [ ] 制約(不変条件)が列挙され、踏み外しを止める柵になっている
- [ ] 凍結契約(変更禁止の形式・IF)と「Xを変えるならYも同時更新」ルールがある

## 新規セッションが辿れるか

- [ ] 「ここから読む」で一次資料・凍結対象・契約の在り処が分かる
- [ ] 検証コード(テスト・デモ/例)がリポジトリに揃い、そのまま実行できる
- [ ] 実装が独立に進められる粒度にマイルストーンが割れている

## 最終確認

- [ ] 対話の中でしか分からない暗黙の前提が、GOAL.mdに明文化されている
- [ ] 「これは対話で決めたが書いていない」判断が残っていない

---

一つでも埋まらない項目は、フェーズ2の実行セッションが計画者の推論を再導出する原因になる。そこが2フェーズ運用の漏れどころ。
