# GOAL.md テンプレート

以下をコピーして各節を埋める。`>` のコメントは埋めたら消す。各節に「なぜ必要か」を添えているので、その意図を満たす内容を書くこと。時系列表現(「追加した」「今後」)を避け、現在の状態を記述する。

---

```markdown
# Goal定義

## ゴール
> 一文で。続けて「完了の定義」(何ができたら終わりか)を書く。
> 実行者が最初に読む一行なので、ここがブレると全部ブレる。

## スコープ / 検証対象
> 何を対象にするか。表で「対象 / やりたいこと / 方式」に分けると実行者が迷わない。

## 非ゴール
> やらないことを明示する。実行者の脱線と過剰実装を防ぐ最も効く節。
> 「なぜやらないか」も一言添えると、実行者が善意で復活させるのを防げる。

## ユーザー / 前提
> 誰のための何か。実装判断の拠り所になる前提(利用者の習熟度・既存資産など)。

## 制約(不変条件)
> 局所的には妥当でも全体で誤る選択を封じるルール。
> 例:「サーバーを立てない」「コアを○○化しない」「凍結ファイルを触らない」。
> 実行者が「良かれと思って」踏み外すのを止める柵。

## 技術方針 / 決定済みアーキテクチャ
> 既に定めた設計判断を、必ず理由付きで。
> 実行者がこれを再議論せずに進められるようにする。

## 不採用(検討して却下した案)
> 却下した代替案とその理由。
> これが無いと、実行者が却下済みの道を「発見」して蒸し返す。先回りして封じる。

## 成功基準
> 客観的・検査可能な基準。理想は各基準が下の検証コードのテストに1対1で対応する。
> 「使いやすい」等の主観語は禁止。「Xを入れるとYが5ステップで出る」のように書く。

## 段階的スコープ / マイルストーン
> 独立に検証できる塊に分解する。各塊に受け入れゲート(合否条件)を付ける。
> 実行フェーズの「実装→レビュー→修正→検証」ループが塊ごとに回る単位。
>   - M1 …: (受け入れ基準)
>   - M2 …: (受け入れ基準)

## 実装ガイド / ここから読む
> 実行する新規セッションへの道案内。
> - 成果物の扱い: どのファイル/ディレクトリが一次資料か、何が凍結か、何が契約か
> - 構成: リポジトリの構造、どこに何を足すか
> - 凍結された契約: 変更禁止のデータ形式・IF。「Xを変えるならYも同時更新」ルール
```

---

## 節を省いてよい場合

小さいタスクでは「ユーザー/前提」「不採用」を省いてよい。ただし **ゴール・非ゴール・制約・成功基準・実装ガイド** は規模に関わらず残す。この5つが「コンテキスト無しの実行者が正しく判断し完了を判定する」ための最小骨格。
