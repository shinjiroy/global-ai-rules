# 人間が読む実務文書の書き方

## 適用範囲

対象は、人間が読むことが前提の実務文書である。README、PR・MR の説明文、Issue 本文、設計ドキュメント、リリースノートが該当する。

次のものは対象外である。従来どおり、AI が効果的に動く書き方を優先する。

- SpecKit の spec.md のような、AI に読ませることが前提の生成物
- エージェント向けのプロンプト、タスク仕様、GOAL.md
- CLAUDE.md、skill、slash command の定義

書籍の章・記事・解説文は対象外である。それらは `../japanese-tech-writing/SKILL.md` を全節適用し、読み物として書くなら `../cognitive-rhythm-writing/SKILL.md` を併用する。

## 手順

作業前に `../japanese-tech-writing/SKILL.md` を読み、次の差分を当てて適用する。

**適用する節**：「論証の厳密さ」「読み手の負荷の管理」「視点と語り」「演出の抑制」「LLM っぽい表現の禁止」「冗長の排除」「見出しの付け方」「読者への誠実さ」。

**適用しない節**：「整形」のうち、脚注への降格と、用語の初出を太字にする規則の二つ。本筋から一段外れる補足は、脚注に降ろすのではなくそもそも書かない。

**「整形」から守るもの**：

- 一文ごとに改行し、段落の区切りは空行で示す。GitHub の PR・Issue 本文は単一の改行をそのまま改行として描画するので、これがそのまま読みやすさになる。README や docs 配下では描画は変わらないが、差分が文単位になってレビューしやすい。
- コード、差分、ログ、設定ファイルの断片はコードブロックで示す。
- ダッシュ（em ダッシュ `—`、horizontal bar `―`、2倍ダッシュ「——」）を日本語の地の文と見出しで使わない。同格・補足の挿入は括弧に、言い換えは句点で二文に分ける。箇条書きで項目とその説明を並べるときは全角コロンで「**項目**：説明」と書く。
- 中黒（・）で語を並列しない。三つ以上並ぶなら箇条書きにする。単一の固有名詞の内部では使ってよい。

**部分的に適用する節**：「段落と論証の構成」からは、一つの段落に一つのトピックだけを置くことと、段落の最初の文を読めばその段落が何の話かわかることの二つだけを取る。論証の運び（反論を処理する位置、山場、伏線の回収）に関する規定は適用しない。

## 分量

読み手が判断または作業をするのに必要な情報だけを書く。

- 背景、設計意図、検討した代替案は、読み手がそれを知らないと判断を誤る場合にだけ書く。書くなら、なぜその選択に至ったかの一文で足りることが多い。
- 変更内容をコードから読み取れる粒度で列挙し直さない。差分を読めばわかることは書かない。
- 見出しだけ置いて中身が一文の節を作らない。その節は本文に畳む。
- 表は、3行以上あり、かつ列をまたいで比較する意味があるときだけ使う。2行の表や、実質1列しか埋まらない表は箇条書きにする。
- 文書の構成や範囲を説明する文（「本ドキュメントでは〜を扱う」「まず〜、次に〜」）を置かない。見出しがその役割を果たす。
