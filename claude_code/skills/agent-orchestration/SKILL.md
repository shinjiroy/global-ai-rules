# サブエージェント・オーケストレーション

## 原理: 難しい判断は計画に前倒しする

高価で難しい統括判断(何を作るか・どう分解するか・どの設計を採るか)は上位モデルとの計画セッションで済ませ、GOAL.md+検証コードに外部化しておく。それが済めば実行は安価なオーケストレーションで回る。**計画に投資するほど実行が安くなる**。この非対称を前提に以下を運用する。

## モデルの割り当て

- **実装(ファイル読み書き・テスト実行・反復)は安価で有能なモデル(Sonnet等)に委任する**。トークン消費が最も重い層で、上位モデルを使っても限界的な品質向上が費用に見合わない
- **レビュー・仕様/品質の分析は上位モデル(Opus等)に委任する**。バグ発見のROIが高く投資に見合う
- **レビューは実装したエージェントとは別のモデル/エージェントに行わせる**。自作の自己レビューは弱いため独立性を確保する。これは他者の成果物を独立した目で見るライター・ベリファイアーであり、自分自身の作業を念のため再確認させる委任とは別物
- **委任した実装にはレビューを出す**。ただし誤りがフォーマット崩れや機械的な置換ミスに限られ、テスト・lint・構文チェックで捕まえきれる変更は、ゲートの実行で代替してよい。エラー処理・制御フロー・外部に見えるインターフェース(CLIのフラグ・API・関数シグネチャ)の変更はここに含めない。迷ったらレビューを出す側に倒す
- **オーケストレータのモデルを自分で選べる場合は、その判断基準を `references/judgment.md` に置いてあるので読む**。既に指定されている場合は読まなくてよい

## オーケストレータのコンテキストを汚さない(最重要)

最上位モデルのコンテキストは最も高価。低価値なトークンを流し込まないこと。

- **長時間サブエージェントを `TaskOutput` の block=true でポーリングしない**。完了通知が自動で届くのでそれに任せる
- **サブエージェントの生の会話トランスクリプト(JSONL等)をオーケストレータのコンテキストに取り込まない**。エージェントの最終報告だけを読む
- 委任すると決めたタスクについて、オーケストレータの仕事は**タスク分解・タスク仕様の作成・受け入れ可否の判断・最終検証**に絞る。委任した実装の手を自分で動かさない(自分でやると決めた小作業を自分で片付けることはこれに反しない)

## サブエージェントの使い回し

- 密結合な逐次作業は同一エージェントを `SendMessage` で使い回すと、コンテキスト/キャッシュを引き継げて効率的
- **使い回すのは、次の作業が前の作業で読んだファイルやそこでの設計判断を参照する場合**。参照しないなら切って新規に立てる。レビューエージェントは対象差分がマイルストーンごとに入れ替わり引き継ぐ価値が薄いので、原則として切る
- レビュー指摘の差し戻しは、実装した本人のエージェントへ `SendMessage` で戻す(新規に立てない)
- コンテキストは単調増加しキャッシュ読み込みコストが膨らむ。1エージェントが担当するマイルストーンは3件までとし、4件目は新規に立てる。これは参照関係による使い回しより優先するハード上限。マイルストーンに分かれていない案件では、扱ったファイル数が数十に達したか、同じ箇所で進捗なく往復し始めたら切る
- 切るときは、前エージェントの最終報告と確定した設計判断を新エージェントのタスク仕様に転記する

## 実行ループ(1マイルストーンあたり)

GOAL.md がマイルストーンに分割済みの案件に適用する。GOAL.md のない単発の委任では、マイルストーン単位の反復を省いて 1〜4 を 1 回だけ回す(仕様源は GOAL.md の代わりに依頼文や ADR)。

1. オーケストレータがタスク仕様(GOAL.mdの該当マイルストーン + 制約 + 受け入れ基準)を書き、実装エージェント(Sonnet等)へ委任
2. 実装完了 → レビューエージェント(Opus等・実装者とは別)へ委任
3. オーケストレータが指摘を実装エージェントへ差し戻して修正させる。再レビューには戻さず 4 へ進む
4. 検証コード(テスト・スモーク)で受け入れ基準を機械的に確認する。落ちたら 3 へ戻る。通れば次のマイルストーンへ。出力は全文を読まず、失敗したテスト名と要点だけをコンテキストに載せる
   - オーケストレータ自身が実行するか、独立したコンテキストの検証エージェントに任せるかは、CLAUDE.md のモデル別の節に従う。検証エージェントを使う場合も受け取るのは最終報告だけ

各ステップでオーケストレータはエージェントの最終報告だけ読み、コンテキストを軽く保つ。

タスク仕様に自己検証の手順を書くかどうかは、**それを受け取るエージェントのモデル**で決める(CLAUDE.md のモデル別の節)。書かない側のモデルに委任する場合は、機械的なゲートで担保する。
