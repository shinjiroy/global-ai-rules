# 「統括の判断」— どのモデルでオーケストレーションするか

Fable 等は Opus 等より高価。オーケストレータにどちらを使うかは、**「統括の判断そのもの」が難しいかどうか**で決める。統括の判断とは、サブエージェントに委任できない決定 —— 何を作るか / どう分解するか / 受け入れるか / どう軌道修正するか。問題は「その決定を下す作業自体が最も高価なモデルの推論を要するのか、一段安価な上位モデルでも同じ結論に至るのか」。

## リトマス試験

> **同じコンテキストを渡した Opus 等に、この決定を任せたら、ほぼ同じ結論を出しそうか?**
>
> - Yes → 難しくない。高価なモデルの代金を払う価値なし。オーケストレータも Opus 等でよい。
> - 決定が「深い領域横断の統合」「本物の曖昧さの解消」に懸かっている → 難しい。高価なモデルの価値が出る。

Opus 等はコードレビューとバグ発見において高い精度と再現率を持ち、100万トークンのコンテキストを扱う。この2点に帰着する判断は Yes 側に倒れやすい。

## 難しい判断(より高価なモデルが正当化される)

- **曖昧・未定義のゴールで、分解を発明しなければならない**。分解を間違えると大量のサブエージェント工数が無駄になる
- **相反する関心事のトレードオフを、正解がない中で秤にかけて決める**
- **領域横断の統合が要る**(例: 専門知識・コストモデル・ゴールを跨いで一つの方針を導く)
- **複数の専門家の食い違う出力のどちらが正しいかを、全部やり直さずに判定する**
- **不可逆・高コストな方向決定**(基本アーキテクチャ、データ契約、何を凍結するか)

## 難しくない判断(Opus 等で十分)

- **ゴールが分解と受け入れ基準を既に明示している**。タスク仕様作成は「発明」でなく「丁寧な書き写し+妥当なデフォルト補完」
- **既知パターンの逐次実行**(実装→レビュー→修正→検証ループ)を回すこと自体は定型
- **客観的ゲートでの受け入れ判断**(テスト・typecheck・build・受け入れ基準チェックリストが通ったか)。深い判断ではなく確認
- **サブエージェントの自信ありげな報告に潜む誤りの検出**(「全テストpass」の裏で、テストが誤った期待値を固定していた等)。コードとして現れる誤りなら Opus 等のレビュー精度で足りる。仕様やゴールの解釈違いが原因で、コードを見ても気づけない類のものだけが高価なモデル向き
- サブエージェント報告の要約・中継、標準的な検証(スモークを流して出力を読む)

## 実用的な線引き

- **ゴールが曖昧で分解から設計する案件ほど高価なモデル向き**
- **ゴールが詳細に決まっている実行案件ほど Opus 等で十分**
- **長いコンテキストを丸ごと保持したまま統合判断する必要があるかを見る**。参照する資料が多くても、個々の判断が局所的なら委任で分割できる。分割すると失われる相互参照が判断の核心にある場合だけ、一つのコンテキストに載せる価値がある

だから2フェーズ運用(計画=高価なモデルとの対話でGOAL.mdを作り込む → 実行=別セッションで/goal)では、計画フェーズで難しい判断を出し切ってあるほど、実行フェーズのオーケストレータは安価な側に落とせる。GOAL.mdが詳細なら、実行の統括の8〜9割は「難しくない」側に収まる。
