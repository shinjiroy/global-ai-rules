# 「統括の判断」— どのモデルでオーケストレーションするか

最上位モデル(Fable等)はOpus等の上位モデルより高価。オーケストレータにそれを使うべきかは、**「統括の判断そのもの」が難しいかどうか**で決める。統括の判断とは、サブエージェントに委任できない決定 —— 何を作るか / どう分解するか / 受け入れるか / どう軌道修正するか。問題は「その決定を下す作業自体が上位モデルの推論を要するのか、中位モデルでも同じ結論に至るのか」。

## リトマス試験

> **同じコンテキストを渡した有能な中位モデル(Opus等)に、この決定を任せたら、ほぼ同じ結論を出しそうか?**
>
> - Yes → 難しくない。最上位モデルの代金を払う価値なし。オーケストレータもOpus等でよい。
> - 決定が「深い領域横断の統合」「本物の曖昧さの解消」「自信ある報告の隠れた誤りの検出」に懸かっている → 難しい。最上位モデルの価値が出る。

## 難しい判断(最上位モデルが正当化される)

- **曖昧・未定義のゴールで、分解を発明しなければならない**。分解を間違えると大量のサブエージェント工数が無駄になる
- **相反する関心事のトレードオフを、正解がない中で秤にかけて決める**
- **領域横断の統合が要る**(例: 専門知識・コストモデル・ゴールを跨いで一つの方針を導く)
- **サブエージェントの自信ありげな報告が、実は微妙に間違っている/抜けていることを見抜く**(「全テストpass」の裏で、テストが誤った期待値を固定していた等。報告を鵜呑みにせず正しさを自分で推論しないと気づけない)
- **複数の専門家の食い違う出力のどちらが正しいかを、全部やり直さずに判定する**
- **不可逆・高コストな方向決定**(基本アーキテクチャ、データ契約、何を凍結するか)

## 難しくない判断(Opus等で十分)

- **ゴールが分解と受け入れ基準を既に明示している**。タスク仕様作成は「発明」でなく「丁寧な書き写し+妥当なデフォルト補完」
- **既知パターンの逐次実行**(実装→レビュー→修正→検証ループ)を回すこと自体は定型
- **客観的ゲートでの受け入れ判断**(テスト・typecheck・build・受け入れ基準チェックリストが通ったか)。深い判断ではなく確認
- サブエージェント報告の要約・中継、標準的な検証(スモークを流して出力を読む)

## 実用的な線引き

- **ゴールが曖昧で分解から設計する案件ほど最上位モデル向き**
- **ゴールが詳細に決まっている実行案件ほどOpus等で十分**

だから2フェーズ運用(計画=最上位モデルとの対話でGOAL.mdを作り込む → 実行=別セッションで/goal)では、計画フェーズで難しい判断を出し切ってあるほど、実行フェーズのオーケストレータは下位に落とせる。GOAL.mdが詳細なら、実行の統括の8〜9割は「難しくない」側に収まる。
